# 项目立意审计（Preflight Audit）

**核心判断：项目能不能成，80% 在起步阶段就决定了。**
本技能用于在动手之前，把项目"为什么做、为谁做、按什么标准算赢、靠什么才算真的新"问到不能含糊，并在每次决策时防止范围膨胀与目标漂移。

> 使用方式：按 P0→P3 四个阶段顺序走，每阶段用对应的"必答问题"逐条作答。
> **答不上来的，就是项目最大的风险**；把它转成"待验证假设"，放进最小验证实验。
> 最后输出：一页结论 + 风险排序 + 下一步唯一动作。

---

## P0 · 锚定目的（不写任何方案前先回答）

用逼问的方式，逐条写出**明确、可检验**的答案，不许写空话。

1. **这个项目最终要拿到什么？** 说具体物：奖项级别？通过某个评审？拿到投资？发表？毕业？
2. **判定"成功"的唯一标准是什么？** 谁的、什么动作、在什么时间点判定？
3. **如果只能保留一件事，保留哪件？**（用来在资源不足时砍东西）
4. **我们现在的资源是什么？** 人（几人、能力）、钱、时间（到哪天）、可借用的设备/场地/数据。
5. **明确不追求什么？** 写下 3 条"我们不打算做"的事，越具体越好。

> 检验：把 1–5 复述给一个不了解项目的人，他能准确说出"你们要干什么、怎么算成功、不干什么"吗？

---

## P1 · 对齐评分口径（把"想做的"换成"被衡量的"）

任何项目都有隐含的评分结构，必须先把它显式化。

1. **评分维度与权重是什么？** 逐项写出数字，没有官方权重就写出你推断的权重并标注"推断"。
2. **每个维度里，最容易拿分的是什么？最容易失分的是什么？**
3. **硬性要求有哪些？**（必须是、不能是、交付物清单、截止时间、格式、合规红线）
4. **哪些要求是"及格线"，哪些是"拉开差距线"？**
5. **裁判/评审是谁？他们见过什么、烦什么、信什么？**（决定表达方式）

> 输出一张表：`维度 | 权重 | 靠什么拿分 | 我们现在的状态（有/无/弱）`
> **权重高的维度如果"弱"或"无"，就是当前最高优先级。**

---

## P2 · 压力测试（用怀疑者视角审一遍）

### 2.1 创新缝隙（"凭什么不是又一个 XX"）

1. 市面上谁在做类似的事？**列出至少 3 个**，越强越好（含本领域巨头与主办方自家产品）。
2. 我们的差异是**功能层、场景层、交付物层、交付模式层、资源组织层**中的哪一层？
3. 如果对手明天就做了同样的功能，我们还剩什么？
4. 一句话说清："**别人做不到/不愿做/做不起的那件事，我们做。**" 那句话是什么？
5. 这个缝隙是**资源壁垒**（渠道、资质、数据）还是**技术/成本优势**？如果是后者，对手跟进的成本是多少？

### 2.2 技术纵深（"这事有难度吗"）

1. 真正的难点是什么？**写出至少一个"外行会卡住、内行才看得出"的难点**。
2. 这个难点是**信号层、特征层、判别层、决策层**中的哪一层？
3. 我们打算靠什么证明"解决了"？指标叫什么、怎么算、目标值多少？
4. 有没有**对照组**？（单模 vs 多模、规则 vs 模型、我们 vs 基线）
5. 如果评委问"你为什么这么做"，我们答得出吗？**答不出的方法就是堆料。**

### 2.3 可复现性（"你们自己还能再跑一遍吗"）

1. 数据从哪来？能合法拿到吗？样本量够吗？
2. 关键步骤能写成脚本吗？换一台电脑能跑起来吗？
3. 如果被人要求"现场重跑一遍"，我们多久能跑出来？
4. 哪些环节依赖"不可获取"的东西（真实设备、特定账号、内部数据）？**这些必须提前找替代。**

### 2.4 目的回归（"我们还在解决最初的问题吗"）

1. 现在做的事情，**逐条对应到 P0 的第 1 条**（最终要拿到的东西）。对应不上的，标红。
2. 现在做的事情，**逐条对应到 P1 的评分维度**。对应不上的，标红。
3. 有没有为了"看起来高级"而增加的东西？**列出来，准备砍。**
4. 有没有为了"更完整"而扩张的范围？**列出来，准备砍或推后。**

---

## P3 · 完备性与取舍（"够不够"与"停在哪"）

**完备 ≠ 功能多。完备 = 该有的有，不该有的没有。**

1. **交付物清单**：逐项列出，标注"必须有 / 加分 / 可无"。
2. **必备能力 vs 可选能力**：画一张 2×2（重要×成本），落在"重要且低成本的"先做；"低价值高成本的"直接砍。
3. **阶段边界**：明确"现在这一阶段只做什么"。**写一张"本阶段不做清单"**，贴在显眼处。
4. **后续阶段的接口**：现在的产物能不能直接被下一阶段用？（数据格式、代码结构、文档）
5. **最坏的三个结局**：
   - 最可能失败的原因是什么？
   - 失败时能留下什么可复用的东西？
   - 有没有 Plan B（降级方案 / 换方向）？

---

## P4 · 漂移检测与最小验证

### 4.1 五种典型漂移（每次讨论后自查）

| 漂移类型 | 表现 | 解药 |
| --- | --- | --- |
| **范围膨胀** | 一直在"再加一个功能" | 回到"本阶段不做清单" |
| **方法堆砌** | 加了方法却说不清为什么 | 每个方法必须对应一个难点+一个指标 |
| **目标遗忘** | 讨论半天，和最初目的无关 | 重读 P0 的第 1 条 |
| **产物替代目的** | 文档/PPT 越写越多，实验没做 | 用"最小验证"打断 |
| **指标替代价值** | 只追求数字好看，不管问题真不真 | 追问"这个数字证明了什么" |

### 4.2 一次只验证一个假设

1. **当前最致命的假设是什么？**（如果它错了，项目就白做）
2. **用最小成本怎么证伪它？**（半天到三天能出结果的动作）
3. **通过 → 继续；不通过 → 走哪条备选？**
4. **下一个假设是什么？**（排队，不要同时验证）

> **规则：不验证完当前假设，不开始搭大工程。**

## 输出模板（每次审计都产出这一页）

```markdown
# <项目名> 立意审计 · <日期>

## 一句话结论
方向：✅ 对头 / ⚠️ 需调整 / ❌ 偏了
完整度：__/10（评分依据：P0–P3 各阶段是否有明确答案）
最大风险：<一句话>

## 评分骨架
| 维度 | 权重 | 我们是否覆盖 | 证据/缺口 |

## 三个最致命的缺口
1. …
2. …
3. …

## 下一步唯一动作
> （只写一件，且是能证伪最致命假设的最小动作）

## 本阶段不做清单
- …

## 下次复盘要回答的问题
- …
```

## 使用纪律

1. **先写结论，再写理由**——防止用论证掩盖判断。
2. **每个"是"都要有证据**（数据、链接、可复现的实验），没有证据就写"待验证"。
3. **不确定就标记不确定**，不要用确定性语气填坑。
4. **一次只推进一步**：审计不是为了写文档，是为了决定"下一步做哪一件事"。
5. **审计要定期重跑**：每次重大决策、每次阶段切换、每次感觉"正在跑偏"时，重跑一遍。
